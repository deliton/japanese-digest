8本の脚を持ち網状の巣を作って獲物を待ち構えるクモは、一見すると人間や哺乳類とはほど遠い生物に思えます。ところが新たな研究により、クモの一種が人間のような レム睡眠 を経験しており、寝不足になると 睡眠負債 が蓄積される可能性があることが判明しました。

研究チームは赤外線カメラを使ってケアシハエトリの動きを監視したり、睡眠中のクモを妨害して反応を調べたり、睡眠を妨げてどうなるのかを調べたりしました。その結果、ケアシハエトリは主に日中に活動しており、夜になると睡眠に適した休息姿勢を取り、レム睡眠と思われる状態になると周囲の妨害に対する反応が鈍くなることが確認されました。

続いて、研究チームはケアシハエトリの睡眠を妨害するため、夜間に25匹の生きたショウジョウバエを飼育ケースの中に入れました。……睡眠を妨害した次の夜、ケアシハエトリは睡眠妨害前の夜と比べて、レム睡眠に似た行動を示す時間が約80％も増加しました。まるで不足したレム睡眠を補おうとするこの現象は レム睡眠反跳 と呼ばれ、クモが実際にレム睡眠のような睡眠状態を必要としている説得力のある証拠だと研究チームは主張しています。

（CNN） 「奇跡の木」として知られるモリンガ（ワサビノキ）は、地球上で最も栄養密度の高い植物の部類に入り、その治癒効果が高く評価されている。今年4月に発表された研究では、このモリンガにもう一つの大きな利点があることが明らかになった。水からマイクロプラスチックを除去する能力が非常に高いというのだ。

原文抜粋（「……」は中略）

大手企業のAIはたいていの場合、主に英語のデータセットを中心に学習しています。新たな研究で、英語であれば適切に処理できるAIが、データが少ない少数言語を処理するときにコストが高くなってしまう可能性があることが示されました。

昨今の生成AIの基盤となる大規模言語モデル(LLM)は、トークナイザーと呼ばれる処理により、文章を単語ごとや文字ごと、場合によってはバイト単位に分割して「トークン」と呼ばれる塊として扱います。大抵の有料型AIはこのトークンの数に応じて料金を課しています。

トークン数で見ると、同じ文章なのに英語は13、マラヤーラム語は26、そしてアムハラ語は78となり、アムハラ語は英語の6倍ものコストがかかってしまうことになります。

そもそも冗長な表現が多い言語もありますが、CLEARが参照したデータセットの中で最も冗長なミャンマーのシャン語でも、文字数で見ると英語より42％長いだけでした。CLEARは「冗長性だけで、トークン数が6倍にもなるのは説明できない」としています。

CLEARによると、インターネット上での使用割合が多いトップ20の言語の最小/最大トークン比率はほとんど1.5倍から3.1倍の間に収まっているものの、それ以外では差異が大きくなり、最大で17倍まで幅が広がることがあるそうです。

原文抜粋（「……」は中略）

キャリアカー(車両を何台も積んで運ぶトラック)のドライバーをしながら、ブラウザで遊べる積み込みゲーム「僕らは陸送屋」を個人で作っています。 コードはほぼ全部 Claude Code (Anthropic のAI開発ツール)に書いてもらっています。絵・効果音・BGM・声も、別の生成AIに作らせました。

AIは1つの会話で何でもやらせるとあちこちを書き換えて壊します。 そこで、リポジトリ直下の CLAUDE.md (AIが会話の最初に必ず読むメモ)に、 役割を3つに分けて書きました 。

開発用サーバーや長い検証を「裏で動かしてあとで結果を見る」ことができませんでした。AIが返事を終えるたびに、裏の処理が消えるためです。「サーバーがたまに落ちる」の正体がこれでした。 対策は、 検証を1コマンドにして、前面で最後まで実行する ことです。

車が輪止めに当たると、画面から車が消えるバグが出ました。原因は関数の中で fm (床の仕組みを持つオブジェクト)が未定義だったことです。 なぜ検証で気づけなかったか。 検証用のスクリプトが、グローバルに window.fm を置いていた からです。本体は fm を定義し忘れていても、グローバルを見つけて動いてしまい、エラーが隠れていました。

教訓は「検証の道具が本体の欠陥を隠すことがある」です。AIに検証まで任せていると、こういうズレに気づきにくいので、 CLAUDE.md に教訓として残しました。

原文抜粋（「……」は中略）

シンプルに書くのしんどいしメンテもしんどかった。 ちゃんと書いてもフレーキーだし、ノーコード系のやつもなんかライブラリのバージョンが上がっただけで全部動かなくなったりするし、マジでしんどかった。

っていうネガティブな理由で主要シナリオに絞っていただけで、これらの負担が減ったなら、網羅的にやったほうがよくない？と思ったのが出発点。

まったくしんどくない。なぜなら書かないから。おわり。 フレーキー問題も、ネイティブアプリだと特にしんどかったけど、AI に伴走させることで失敗の原因調査やテストの修正はだいぶ楽になってきてる

既存のユニットテストなどと違って E2E ではより抽象度の高い " シナリオ " を扱う。 広く整備しようとすると、日々増えたり変わったり消えたりする機能に、シナリオも追従させる必要がある。主要シナリオだけと割り切っていたときにはなかっためんどくささが出てくる。

なので、「どの実装を、どのシナリオで確認するか」を対応表にした。

導入時の不足を baseline として保存し、通常の PR では新しい不足を追加できないようにした。 毎回「あとでやる」で通せてしまうのを防ぐため。
